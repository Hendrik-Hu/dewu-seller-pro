# 卖家库存助手加速研发路线

> 制定日期：2026-08-13<br>
> 当前正式基线：v0.21.0 Android 闭测版<br>
> 当前开发分支：`codex/v0.22.0-mobile-ux-system`<br>
> 核心目标：快速完成小微卖家业务闭环，随后主攻可执行 AI Agent

## 1. 研发策略调整

从本阶段开始，不再把安全治理和边角校验作为独立主线。资源分配调整为：

| 方向 | 建议投入 | 说明 |
| --- | ---: | --- |
| 核心业务闭环 | 50% | 入库、查货、订单、履约、退回、结算 |
| AI Agent | 25% | 业务工具、上下文、规划、执行与评测 |
| 快速录入与商品库 | 15% | OCR、条码、商品候选和纠错 |
| 移动体验 | 5% | 只优化高频路径，不做无目标美化 |
| 必要质量门槛 | 5% | 使用现有自动化测试，只补本次改动的高风险边界 |

## 2. 不再重复投入的工作

- 不再进行与当前功能无关的大范围 RLS 或权限审计；
- 不在每个小改动后重新构建签名 APK/AAB；
- 不为闭测阶段继续扩展营销网页；
- 不为低频设置页进行反复视觉打磨；
- 不提前建设覆盖所有品牌的完整商品数据库；
- 不尝试通过爬虫、自动登录或非公开接口抓取得物账号；
- 不把每个版本都包装成正式发布版本；
- 不重复验证已经由自动化测试稳定覆盖的旧功能。

## 3. 必须保留的最低底线

以下能力直接保护用户库存、成本和账号，不能为了速度拆除：

- 用户数据继续由 RLS 隔离；
- 入库、出库、调拨、恢复和结算继续走事务 RPC；
- operationId 幂等继续防止重复扣减或重复增加库存；
- AI 写操作继续经过结构化计划和用户确认；
- 软删除、活动账本和备份恢复继续保留；
- 涉及金额和库存的新改动必须补最小业务测试；
- 每个大版本只运行一次现有测试、TypeScript 和生产构建门槛。

## 4. 里程碑一：v0.22 移动体验收口

### 目标

让现有功能在手机上更容易找到和操作，不新增大型业务模块。

### 工作范围

- 收口当前 8 个未提交界面文件；
- 统一页面边距、标题、表单、弹窗、按钮和底部导航；
- 压缩首页和统计页信息密度；
- 优化入库、出库、库存搜索和仓库切换；
- 确保 390×844 常见移动尺寸无溢出和遮挡；
- 把复杂说明收进上下文帮助，不占据主流程；
- 提交、截图、合并并形成一个可回溯版本。

### 完成标准

- 入库、查货和出库主路径可以单手完成；
- 所有主要点击区域不小于移动端合理触控尺寸；
- 现有 176 项测试、TypeScript 和 Android 资源构建通过；
- 真实账号只读验收，不改动用户库存。

## 5. 里程碑二：销售订单与履约闭环

### 目标

把“卖出一双鞋”从一次库存扣减升级为持续可跟踪的订单。

### 最小状态链

```text
已成交
  -> 待发货
  -> 已发货
  -> 平台收货/鉴别中
  -> 鉴别通过
  -> 已结算

异常分支：
取消 / 超时 / 鉴别失败 / 退回 / 退款
```

### 工作范围

- 新建独立销售订单对象；
- 订单绑定商品变体、仓库、数量、售价和费用快照；
- 区分库存占用、实际出库和逆向恢复；
- 首页增加待发货、待鉴别、待结算和异常待办；
- 实际结算关联订单，不再只依赖孤立出库流水；
- 支持取消、鉴别失败和退回后的库存恢复；
- 所有逆向操作保留账本记录。

### 完成标准

- 一笔订单可以从成交走到结算；
- 取消和鉴别失败不会造成库存丢失或重复恢复；
- 用户可以清楚看到“下一步要做什么”；
- 订单状态与库存数量一致。

## 6. 里程碑三：商品主数据与全局查货

### 目标

解决同一货号在不同仓库出现不同名称、品牌和图片的问题，为商品库、OCR 和 Agent 提供稳定基础。

### 数据分层

```text
商品主档 Product
  -> 款式/配色 Style
  -> 尺码变体 Variant
  -> 仓库库存 Inventory
  -> 具体位置 Location
```

### 工作范围

- 名称、品牌、货号和主图进入商品主档；
- 尺码成为商品变体；
- 仓库、数量、平均成本和库位成为库存记录；
- 默认提供全仓搜索，再按仓库筛选；
- 商品详情集中显示所有尺码、仓库和位置；
- 设计用户纠错和商品合并机制；
- 兼容并迁移现有库存数据，不破坏历史账本。

### 完成标准

- 同一 SKU 不再跨仓漂移名称和品牌；
- 搜索一次即可知道鞋在哪个仓库和位置；
- OCR、条码和 Agent 可以引用稳定 productId/variantId；
- 现有活动流水仍可追溯。

## 7. 里程碑四：OCR、扫码与商品候选 MVP

### 目标

显著缩短第一次录入新商品的时间，但不让错误识别直接污染库存。

### 第一版流程

```text
拍摄鞋盒侧标 / 扫描条码
  -> 图像质量检查
  -> OCR 提取品牌、货号、尺码、条码
  -> 查询商品候选
  -> 显示来源、时间和置信度
  -> 用户确认或修改
  -> 生成入库草稿
  -> 保存入库
```

### 工作范围

- Android 相机拍摄和条码扫描；
- OCR 提取文本与结构化字段；
- 优先匹配用户自己的历史商品；
- 建立小规模人工审核商品候选库；
- 保存用户纠错结果，为后续商品库积累数据；
- 识别失败时无缝回到手工录入；
- 禁止识别结果未经确认直接写数据库。

### 完成标准

- 常见鞋盒标签可以自动填入货号和尺码候选；
- 用户能看见识别来源和不确定字段；
- 识别失败不会阻断入库；
- 完成一次新商品入库的平均步骤明显少于纯手工流程。

## 8. 里程碑五：AI Agent v1

### 目标

把当前“AI 聊天 + 计划”升级为能够理解卖家目标、调用多个业务工具、持续完成任务的经营 Agent。

### 8.1 Agent 工具层

第一批稳定工具：

- `inventory_search`：查询 SKU、尺码、仓库、位置和成本；
- `inventory_summary`：库存、资金占用、库存年龄和异常；
- `product_match`：商品库和 OCR 候选查询；
- `inbound_draft`：生成入库草稿；
- `outbound_quote`：计算费用、保本价和目标售价；
- `sales_order_create`：生成销售订单草稿；
- `order_next_action`：查询待发、待鉴别、待结算事项；
- `profit_analysis`：解释预计和实际利润差异；
- `inventory_health`：发现异常和滞销库存。

### 8.2 Agent 工作方式

- 默认先读取和分析；
- 需要修改库存或订单时生成结构化计划；
- 高风险动作继续由用户确认；
- Agent 只调用稳定业务工具，不直接拼接数据库更新；
- 记录每次工具调用、结果和失败原因；
- 保留用户偏好：主仓、常用费用方案、默认销售平台和常用表达；
- 不把无限聊天历史当作长期记忆。

### 8.3 第一批 Agent 场景

1. “帮我把这三张鞋盒标签录成入库草稿。”
2. “DD1391 42 码最低卖多少不亏？”
3. “今天有哪些订单需要发货？”
4. “哪些库存压了 90 天以上？”
5. “本月为什么实际利润低于预计利润？”
6. “把主仓 Nike 42 码库存调 2 双到工作室。”
7. “检查库存里有哪些成本缺失或主数据冲突。”

### 8.4 Agent 评测

评测重点不是模型聊天是否自然，而是：

- 是否选择了正确工具；
- SKU、尺码、仓库和金额是否提取正确；
- 是否使用真实数据库结果；
- 缺失信息时是否询问而不是猜测；
- 是否在写操作前生成正确计划；
- 重复确认是否不会重复执行；
- 失败后能否解释并继续任务。

### 完成标准

- 至少 50 个真实卖家场景形成固定评测集；
- 查询场景能给出可追溯数据来源；
- 多步骤任务可以连续调用工具完成；
- Agent 错误不能绕过库存和订单业务规则；
- 用户可以清楚撤销草稿、拒绝计划或改用手工流程。

## 9. 里程碑六：闭测与发布准备

### 目标

不再只靠开发者自己模拟，使用真实小微卖家完成闭环验证。

### 工作范围

- 邀请 5–10 位不同库存规模的卖家；
- 让用户完成首次建仓、批量入库、查货、成交、发货、结算和恢复；
- 记录任务时间、失败次数和放弃点；
- 只修复阻断使用、导致数据错误或高频困扰的问题；
- 配置自有域名和 Custom SMTP；
- 完成注册确认与密码恢复整链；
- 建立可信 APK 分发或应用商店发布渠道；
- 明确版本升级、数据迁移和问题反馈机制。

### 完成标准

- 核心流程没有阻断级问题；
- 真实闭测期间没有不可恢复的数据丢失；
- 新用户可以不依赖开发者完成首次入库；
- 发布门槛脚本通过；
- Android 安装、升级和回滚路径明确。

## 10. 版本节奏

建议不再为每个小补丁发布版本，只在完成一个可验收能力后发布：

| 版本 | 主题 | 是否发布 APK |
| --- | --- | --- |
| v0.22 | 移动体验收口 | 是，作为下一闭测包 |
| v0.23 | 销售订单与履约闭环 | 是 |
| v0.24 | 商品主数据与全局查货 | 是 |
| v0.25 | OCR/条码快速入库 MVP | 是 |
| v0.26 | AI Agent v1 | 是 |
| v0.27 | 真实卖家闭测修复 | 是 |
| v1.0 | 满足公开发布门槛 | 正式候选 |

中间普通修复进入开发分支，不反复打包、截图、签名和发布。

## 11. 每个里程碑的最小验证

为了加速，每个大版本只做以下验证：

1. 运行现有自动化测试；
2. 运行 TypeScript 检查；
3. 只为新增业务规则补测试；
4. 对涉及库存或金额的事务做一次回滚烟测；
5. 在 390×844 真机尺寸验证本次主流程；
6. 生成一张关键界面截图和一份简短版本记录；
7. 大版本才构建签名 APK/AAB。

## 12. 当前立即执行顺序

1. 保留现有 v0.21.0 正式基线；
2. 整理和验收当前 v0.22.0 未提交视觉草稿；
3. 不再继续扩展视觉设计；
4. 建立销售订单数据模型和状态转换表；
5. 先完成手工订单闭环，再接 OCR 和 Agent；
6. Agent 工具契约与订单/商品数据模型同步设计；
7. 每完成一个里程碑再统一截图、提交、打包和记录。

## 13. 决策原则

当出现多个待办时，按以下顺序选择：

1. 是否阻断卖家完成入库、查货、出库或结算；
2. 是否可能让库存、成本或利润出错；
3. 是否显著减少高频任务步骤；
4. 是否为 OCR、商品库或 Agent 提供稳定基础；
5. 是否只是视觉偏好或低频边角问题。

只有前四类进入当前主线，第五类进入待办池。
